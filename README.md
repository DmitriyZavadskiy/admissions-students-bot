# Design-Doc: Чат-бот / RAG-система  

## 1. Контекст проекта  

### 1.1 Бизнес-задача  
- Проблема: абитуриенты и их родители часто не могут быстро найти точную информацию о поступлении (программы, сроки, документы, требования, конкурс, общежитие) в длинных PDF и на страницах сайта. По этой причине часто  возникают повторяющиеся вопросы, (которые соответсвенно дают нагрузку на поддержку)
- Почему чат-бот / RAG-система: нужные знания уже есть в официальных источниках (PDF, страницы сайта, FAQ), но их трудно найти быстро собрать в один понятный ответ. RAG позволяет 1. найти актуальные фрагменты в базе знаний и 2. сгенерировать понятный ответ на русском языке, подкрепив его ссылками на источники  
- Критерии успеха: бот даёт понятные ответы на типовые вопросы и всегда прикладывает источники, уменьшается доля простых вопросов на которые вполне в состоянии ответить боту нежели человеку с поддержки. Повышается удовлетворённость пользователей качеством и ясностью ответов

### 1.2 Целевая аудитория и пользователи  
- Пользователи: абитуриенты и их родители. *дополнительно* - сотрудники приёмной комиссии для разгрузки от типовых вопросов  
- Сценарии использования: реализованы консольный текстовый чат и Telegram-бот поверх того же RAG pipeline.
- Нагрузка: *на этапе MVP ожидаются десятки–сотни диалогов в день в период приёмной кампании, пиковые часы - вечером и в дни дедлайнов подачи документов*  

### 1.3 Ограничения и допущения  
- Доменное ограничение: бот отвечает только по теме “поступление в университет” (сроки, документы, требования, программы, направления, общежитие, стипендии, контакты).  
- Ограничение по источникам: используются только официальные и открытые материалы (PDF/страницы сайта/FAQ).  
- Поведение при отсутствии ответа: если в базе знаний нет нужной информации, бот сообщает об этом и предлагает ссылку на официальный источник и контакты. 

## 2. Архитектура решения  

### 2.1 Общая схема  
- чат интерфейс - API - retrieval по базе знаний - LLM - пост обработка - ответ пользователю
- база знаний хранит документы/чанки + метаданные и векторный индекс. при каждом запросе пользователя backend создает эмбеддинг запроса, делает поиск top k чанков, формирует контекст, отправляет в LLM по промпт шаблону и затем форматирует ответ и добавляет ссылки
- промпт шаблон хранится в репозитории в отдельном файле  

### 2.2 Хранилище знаний / документооборот  
- Источники знаний: Правила приёма PDF, FAQ, страницы программ или направлений, сроки и этапы кампании, список документов и требования, контакты  
- Предобработка: извлечение текста из PDF/HTML, очистка мусор, дубли шапок и тд, нормализация списков, разбиение на смысловые чанки  
- Обновление данных: *на MVP - ручное обновление при выходе новой версии страниц -> далее - скрипт, который по списку URL и папке PDF пересобирает чанки и индекс*  

### 2.3 Retrieval + Generation  
- Retrieval: Qdrant для основной версии MVP и локальные эксперименты для сравнения методов поиска. В экспериментах проверялись dense search, BM25, hybrid dense + BM25 и reranker.
- Обогащение чанков: к каждому чанку добавляются опорные вопросы, краткая суммаризация и идентификаторы соседних чанков, а из таблицы стоимости строятся структурные мини-чанки вида «программа → цена». Индексация и поиск идут по полю `index_text` (суммаризация + опорные вопросы + текст). Готовый набор лежит в `data/processed/enriched_chunks.json`.
- Generation: локальная LLM Qwen2.5-7B-Instruct в формате GGUF. Модель получает только найденный контекст и должна отвечать по нему, без выдумывания фактов.
- Контроль ответа: ответы со ссылками на источники, при низкой релевантности retrieval или отсутствии ответа - fallback не нашёл в источниках + контакты и ссылки  

### 2.4 Интеграции и интерфейсы  
- Интерфейсы: консольный режим `python -m scripts rag` и Telegram-бот `python -m telegram` поверх той же функции ответа. Простой веб-интерфейс можно добавить позже.
- Протоколы: для Telegram подойдет webhook или long polling. REST API можно добавить позже, если нужен отдельный frontend.

### 2.5 Инфраструктура и развертывание  
- Развёртывание: Docker-контейнер 
- Вычисления: retrieval и индексация могут запускаться на CPU. Генерация через Qwen2.5-7B-Instruct работает на GPU: `llama-cpp-python` собран с поддержкой CUDA и запускается с `gpu_layers=-1`. Запуск на облачном GPU для постоянной доступности — в планах.
  

## 3. Данные и качество знаний  

### 3.1 Сбор и предобработка данных  
- Источники и форматы: PDF с правилами приема и приложениями, а также страницы из `data/raw/urls.txt` при запуске HTML-парсинга. Для боевого запуска база обновлена до материалов приёмной кампании 2026 года (правила, сроки, индивидуальные достижения, олимпиады, стоимость, количество мест, общежития).
- Шаги предобработки: извлечение текста из PDF/HTML, очистка и нормализация текста, разбиение на смысловые чанки. обработка списков/таблиц из PDF и устранение артефактов такие как переносы строк, номера страниц*  
- Метаданные: к каждому чанку добавляются ссылка на источник, название документа, раздел, актуальность/дата версии, тип источника правила/FAQ/программа/контакты  

### 3.2 Векторизация и индексирование  
- Embedding-модель: sentence-embedding модель для русского языка из  SentenceTransformers фиксируется название  
- Индекс: в основном MVP используется Qdrant, метрика cosine. В экспериментальных скриптах дополнительно используется локальный поиск, чтобы быстро сравнивать dense, BM25, hybrid retrieval и rerank без постоянной пересборки Qdrant.
- Обновление: пересборка индекса при обновлении документов, позже  - инкрементальное обновление  

### 3.3 Метрики качества знаний  
- Покрытие: доля ключевых сценариев (сроки, документы, требования, программы, общежитие, стипендии, контакты), которые имеют поддержку в базе знаний  
- Актуальность: наличие даты/версии источников. скорость обновления базы при изменении правил например, обновление в течение N дней после публикации
- Как находим спорные места: составляем список триггерных тем где чаще бывают расхождения и ошибки, *дополнительно: отмечаем спорные места по сигналам качества*
- Консистентность: отсутствие дублей и противоречий. ручная ревизия спорных мест.
- Спорные места: отслеживаем по триггерным темам: сроки подачи, перечень документов, квоты и льготы, общежитие условия

## 4. Модель и генерация  

### 4.1 Выбор LLM и промптинг  
- Модель: для генерации использовалась локальная `Qwen2.5-7B-Instruct` в GGUF-квантизации `Q4_K_M`. Модель выбрана как open-source вариант, который нормально работает с русским языком и может запускаться локально без передачи данных во внешний API.
- Промпт-шаблон: отвечать только по контексту, не придумывать числа, даты, телефоны, email и условия поступления, а также указывать источник. Если точного ответа в контексте нет, модель должна прямо сказать, что точной информации нет.
- Ограничения: top-k контекстов, максимальная длина контекста, максимальное число токенов ответа и скорость генерации на доступном железе.
- требования к приватности: требования к приватности на MVP минимальные так как система работает по публичным документам университета.
  персональные данные не запрашиваем а также историю чата не храним

### 4.2 Контроль качества ответов  
- Метрики: точность соответствия ожидаемому ответу, полнота, отсутствие галлюцинаций и наличие ссылки на источник.
- Ошибки: галлюцинации, неполный ответ, устаревшие сведения  
- Механизмы: fallback при отсутствии контекста запрет на домысливание вывод источников. *эвристика уверенности если similarity < threshold -> fallback  

### 4.3 Обучение/дообучение  
- На текущем этапе: fine-tuning не обязателен. упор на качество retrieval, чанкинга и промптинга.  
- Возможно использование набора вопросов для улучшения промптов retrieval или последующего дообучения. версионирование моделей и возможность rollback  

## 5. UX / пользовательский опыт  

### 5.1 Сценарии взаимодействия  
- Основные сценарии: приветствие, вопрос-> поиск по знаниям-> ответ. уточняющий вопрос при нехватке данных. многошаговый диалог для уточнений.  
- Исключительные сценарии: нет ответа fallback + ссылки/контакты, не поняли вопрос просим переформулировать, баг/ошибка сообщение “напишите чуть позднее” 


### 5.2 Диалоговая логика  
- Режим: single-turn для большинства вопросов + уточняющие вопросы  при необходимости например, уровень обучения, форма обучения  
- Контекст: хранение короткого окна истории диалога для уточнений. *Хранение истории на MVP можно сделать опциональным и обезличенным*  
- Тон/стиль: простой русский язык, короткие абзацы, списки 

### 5.3 Метрики UX  
- Время до первого ответа и среднее время ответа  
- Доля успешных диалогов   
- Сбор фидбэка: короткая оценка полезности. логирование ответов и выбранных источников для улучшения качества 

## 6. Безопасность, соответствие и этика  
- Персональные данные: на MVP не реализуем маскирование ПДн, предполагаем что пользователь не вводит персональные данные. также в интерфейсе предупреждаем не отправлять паспорт, телефон, адрес и любые другие ЧД которые могут идентифицировать пользователя 
- Приватность и источники: база знаний формируется из официальных открытых документов. ответы содержат ссылки на источники для проверки и снижения риска дезинформации  
- Анти-галлюцинации и репутационные риски: бот не должен выдумывать факты. при отсутствии информации - честный ответ и перенаправление на официальные контакты  
- Прозрачность и этика: пользователь информируется, что общается с ботом  

## 7. План внедрения и эксплуатации

- Фаза 0: согласование домена/датасета, подготовка источников, дизайн-док  
- Фаза 1: MVP - парсинг/чанкинг, векторная база, retrieval + генерация, простой интерфейс, базовый набор тестовых вопросов

- Мониторинг: логирование ошибок, базовые метрики latency, доля fallback  
- Обновление знаний: ручное обновление документов и пересборка индекса

## 8. Риски и допущения  
- Риск: вопросы, что делаем: отказ отвечать вне домена и перенаправление на официальные источники 
- Риск: грубость, что делаем: нейтральный ответ и отказ от грубых ответов  
- Риск: prompt injection и плюс дополнительно попытка заставить игнорировать правила, что делаем: инструкция отвечать только по контексту
- Риск: запросы, связанные с чем-то незаконным или сильно отдаленным от функционала: отказ отвечать на такие темы и возвращение к теме поступления

## 9. Бюджет и ресурсы  
- Человеческие ресурсы:  
  - 1 разработчик 
- Технологические ресурсы:  
  - CPU достаточно для парсинга, чанкинга, индексации и retrieval-экспериментов. Для комфортной генерации ответов локальной Qwen2.5-7B-Instruct использовалась GPU.
- Примерные затраты:  
  - минимальные при локальном запуске. Основные затраты - железо и время выполнения локальной модели; внешняя облачная LLM в текущей реализации не используется.
- ROI оценки:  
  - снижение нагрузки на сотрудников поддержки по типовым вопросам, ускорение получения ответов, рост удовлетворённости абитуриентов  

## 10. Экспериментальная оценка

### 10.1 Сеттинг экспериментов

В экспериментах фиксировалась одна и та же база документов, чтобы сравнивать именно методы поиска и генерации, а не разные наборы источников. Основной pipeline такой:

- документы из `data/raw/pdfs` и `data/raw/urls.txt` извлекаются в `data/processed/documents.json`;
- документы режутся на чанки и сохраняются в `data/processed/chunks.json` или в экспериментальные файлы `data/processed/chunk_experiments`;
- чанки проходят предобработку (`prep_heads`) и обогащение метаданными (`enrich_chunks`), итоговый набор для бота — `data/processed/enriched_chunks.json`;
- для основной MVP-версии чанки загружаются в Qdrant в коллекцию `admissions_chunks`;
- для экспериментов retrieval дополнительно используется локальный поиск по тем же чанкам, чтобы быстро сравнить dense, BM25, hybrid и reranker без пересоздания Qdrant-коллекции.

Qdrant в этой работе нужен как векторное хранилище для реального запуска бота. В экспериментальной части он не является переменной: меняются чанкинг, эмбеддер, способ поиска и reranker, а набор документов остается тем же.

### 10.2 Датасеты

Датасет для retrieval строится из официальных материалов по поступлению:

- `data/raw/pdfs` - PDF с правилами приема и приложениями;
- `data/raw/urls.txt` - список страниц, если нужно подтянуть HTML-источники;
- `data/processed/documents.json` - извлеченные документы. У каждого документа есть `id`, `title`, `source`, `type`, `text`;
- `data/processed/chunks.json` - чанки документов. У чанка есть `chunk_id`, `doc_id`, `source`, `title`, `type`, `text`, границы в исходном тексте и параметры чанкинга.

Тестовый датасет лежит в `data/eval`:

- `gold_qa.json` - первоначальный набор вопросов;
- `gold_qa_enriched.json` - 50 вопросов с добавленными `expected_answer`, `expected_chunk_ids`, `relevant_terms`, `relevant_text`;
- `gold_qa_extended.json` - 65 вопросов. К исходным вопросам добавлены категории `contacts`, `dormitory`, `documents`, `programs`, `conditions`.

Вопросы собирались вручную и полуавтоматически из реально проверяемых фрагментов документов. Для каждого вопроса фиксировался ожидаемый документ, ожидаемый ответ и релевантный фрагмент. Это важно, потому что проверка идет не просто по названию PDF, а по попаданию нужного чанка или нужного текста в найденный контекст.

### 10.3 Как считается попадание в контекст

Для каждого вопроса есть список `expected_chunk_ids` или `relevant_text`. Ответ retrieval считается успешным, если среди top-k найденных чанков есть чанк, который совпадает с ожидаемым `chunk_id` или содержит релевантный текст. Для экспериментов с разным размером чанка старые `chunk_id` не всегда совпадают буквально, поэтому дополнительно используется проверка по `relevant_text` и ключевым терминам.

Такой подход честнее, чем проверка только по `expected_doc`: один PDF может быть большим, и попадание в правильный документ еще не значит, что модель нашла правильное место внутри него.

### 10.4 Метрики retrieval

- `Hit@1` - правильный фрагмент стоит на первом месте. Это самая строгая метрика для поиска.
- `Hit@5` - правильный фрагмент попал в первые 5 найденных чанков. Это важно для RAG, потому что LLM обычно получает несколько фрагментов контекста.
- `MRR` - средний обратный ранг первого правильного фрагмента. Чем выше правильный фрагмент в выдаче, тем лучше.
- `MAP` - средняя точность по всем релевантным фрагментам. Нужна, если у вопроса может быть больше одного подходящего чанка.
- `NDCG@5` - качество ранжирования в top-5 с учетом позиции релевантных фрагментов. Полезна для оценки reranker, потому что он должен не только найти правильный чанк, но и поднять его выше.

### 10.5 Baseline

Baseline повторяет начальную схему проекта: чанкинг около `1600/250`, эмбеддер `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`, dense search.

> Примечание: таблицы в README приведены на исходном наборе из 50 вопросов; в отчёте о проекте те же эксперименты пересчитаны на расширенном наборе из 65 вопросов.

| вариант | вопросы | чанки | Hit@1 | Hit@5 | MRR | MAP | NDCG@5 |
|---|---:|---:|---:|---:|---:|---:|---:|
| baseline MiniLM dense | 50 | 178 | 0.140 | 0.540 | 0.325 | 0.343 | 0.286 |

Вывод: baseline находит правильный фрагмент в top-5 примерно в половине случаев, но первый результат часто неверный. Поэтому дальше отдельно проверялись чанкинг, эмбеддеры, sparse/hybrid retrieval и reranker.

### 10.6 Эксперимент с чанкингом

Проверялись два способа чанкинга: фиксированное окно по символам и sentence-aware чанкинг. Размеры: `700/100`, `1000/150`, `1600/250`, `2200/300`.

| вариант | Hit@1 | Hit@5 | MRR | MAP | NDCG@5 |
|---|---:|---:|---:|---:|---:|
| sentence 700/100 | 0.160 | 0.540 | 0.311 | 0.350 | 0.282 |
| sentence 1000/150 | 0.180 | 0.560 | 0.356 | 0.331 | 0.293 |
| sentence 1600/250 | 0.140 | 0.540 | 0.325 | 0.343 | 0.286 |
| sentence 2200/300 | 0.160 | 0.640 | 0.351 | 0.363 | 0.303 |
| fixed 700/100 | 0.220 | 0.560 | 0.364 | 0.351 | 0.342 |
| fixed 1000/150 | 0.200 | 0.540 | 0.346 | 0.344 | 0.276 |
| fixed 1600/250 | 0.160 | 0.520 | 0.334 | 0.332 | 0.282 |
| fixed 2200/300 | 0.140 | 0.640 | 0.349 | 0.379 | 0.336 |

Лучший вариант по Hit@1 и NDCG@5 - `fixed 700/100`. Большие чанки иногда дают высокий Hit@5, но хуже ставят правильный фрагмент на первое место. Для дальнейших экспериментов выбран `fixed 700/100`.

### 10.7 Предобработка

После выбора чанкинга проверялись варианты предобработки: сырой текст, очистка пробелов, удаление навигационных блоков, нормализация дат/цен/телефонов и сохранение заголовков в чанках.

| вариант | Hit@1 | Hit@5 | MRR | MAP | NDCG@5 |
|---|---:|---:|---:|---:|---:|
| raw | 0.538 | 0.846 | 0.667 | 0.609 | 0.598 |
| clean | 0.538 | 0.846 | 0.667 | 0.609 | 0.598 |
| nav | 0.554 | 0.846 | 0.680 | 0.637 | 0.631 |
| norm | 0.554 | 0.846 | 0.682 | 0.637 | 0.626 |
| heads | 0.554 | 0.862 | 0.687 | 0.618 | 0.614 |

Удаление навигационного мусора и нормализация значений улучшают ранжирование. В финальной схеме используется `heads`, потому что сохранение заголовков дает лучший Hit@5 и помогает LLM понимать, из какого раздела взят фрагмент.

### 10.8 Эмбеддеры, BM25 и hybrid retrieval

Сравнивались три эмбеддера, BM25 и hybrid retrieval:

- `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`;
- `intfloat/multilingual-e5-small`;
- `sentence-transformers/distiluse-base-multilingual-cased-v2`;
- BM25 как sparse-поиск;
- hybrid dense + BM25 с весом dense `0.65`.

| вариант | Hit@1 | Hit@5 | MRR | MAP | NDCG@5 |
|---|---:|---:|---:|---:|---:|
| dense_mini | 0.220 | 0.560 | 0.364 | 0.351 | 0.342 |
| dense_e5 | 0.480 | 0.660 | 0.570 | 0.524 | 0.533 |
| dense_distil | 0.440 | 0.540 | 0.503 | 0.452 | 0.456 |
| bm25 | 0.320 | 0.760 | 0.511 | 0.427 | 0.407 |
| hybrid_mini | 0.280 | 0.640 | 0.453 | 0.432 | 0.355 |
| hybrid_mini_rerank25 | 0.440 | 0.820 | 0.583 | 0.496 | 0.544 |
| hybrid_e5 | 0.580 | 0.900 | 0.708 | 0.636 | 0.617 |
| hybrid_e5_rerank25 | 0.420 | 0.840 | 0.574 | 0.577 | 0.554 |

Лучший общий retrieval на 50 вопросах - `hybrid_e5`: `intfloat/multilingual-e5-small + BM25`. Он сильно лучше baseline по всем основным метрикам. BM25 сам по себе хорошо поднимает Hit@5, потому что точные слова из вопросов часто совпадают с документами, но хуже ранжирует первый результат. Hybrid соединяет сильные стороны dense и sparse поиска.

### 10.9 Реранжирование

Реранжирование проверялось на расширенном датасете из 65 вопросов. Использовались `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` и `cross-encoder/ms-marco-MiniLM-L6-v2`, разные значения `rerank_top_n`.

| вариант | Hit@1 | Hit@5 | MRR | MAP | NDCG@5 |
|---|---:|---:|---:|---:|---:|
| base | 0.554 | 0.862 | 0.687 | 0.618 | 0.614 |
| mmarco_t10 | 0.508 | 0.831 | 0.649 | 0.591 | 0.614 |
| mmarco_t15 | 0.538 | 0.846 | 0.686 | 0.635 | 0.649 |
| mmarco_t25 | 0.508 | 0.846 | 0.665 | 0.634 | 0.637 |
| mmarco_t50 | 0.508 | 0.846 | 0.655 | 0.639 | 0.624 |
| msmarco_t25 | 0.308 | 0.523 | 0.437 | 0.466 | 0.343 |

Реранкер `mmarco_t15` улучшает `MAP` и `NDCG@5`, то есть делает порядок внутри top-5 лучше. Но по Hit@1 и Hit@5 базовый `hybrid_e5` остается сильнее. По категориям видно, что reranker помогает контактам и датам, но хуже работает на вопросах про стоимость. Поэтому в финальной генерации используется адаптивная схема: reranker применяется не для всех категорий, а для вопросов про стоимость пропускается.

Дополнительно замерена задержка реранкера: время растёт почти линейно по числу кандидатов, `mmarco` быстрее `msmarco`, а `mmarco_t15` даёт лучший компромисс качество/задержка — большие `rerank_top_n` почти не улучшают метрики, но обходятся в разы дороже.

### 10.10 Генерация и ее оценка

Для генерации брали top-5 контекстов из лучшей retrieval-схемы. Проверялись два режима:

- `extractive` - без LLM, ответ собирается из найденного фрагмента;
- `llm` - ответ генерирует `Qwen2.5-7B-Instruct` по найденному контексту.

| режим | accuracy | completeness | hallucination_free | source_reference |
|---|---:|---:|---:|---:|
| extractive | 0.262 | 0.396 | 1.000 | 1.000 |
| Qwen2.5-7B-Instruct | 0.554 | 0.639 | 1.000 | 1.000 |

`accuracy` здесь оценивает уже не поиск, а готовый ответ: найден ли основной ожидаемый факт. `completeness` показывает, насколько полно ответ покрывает ключевые факты из `expected_answer`. `hallucination_free` проверяет, что ответ не добавляет факты вне контекста. `source_reference` проверяет, что в ответе есть источник.

LLM заметно лучше extractive-режима, потому что умеет собрать ответ из найденного фрагмента человеческим языком. При этом слабое место остается в категориях `cost` и `documents`: вопросы про стоимость часто требуют точного сопоставления программы и цены в таблице, а обычный RAG по чанкам не всегда надежно решает такую задачу.

Чтобы закрыть категорию `cost`, чанки были обогащены метаданными и структурными мини-чанками «программа → цена». После этого Hit@1 по `cost` в retrieval вырос с 0.320 до 1.000, а точность генерации на `cost` — с 0.360 до 0.840, при росте общей accuracy генерации с 0.554 до 0.723. Добавление соседних чанков в контекст генерации пользы не дало и было отброшено.

### 10.11 Итог по экспериментам

Главный прирост качества дал переход от MiniLM dense baseline к `e5 + BM25`. Изменение чанкинга тоже помогло, но само по себе не решило проблему. Предобработка дала умеренное улучшение, особенно когда сохранялись заголовки и убирался навигационный мусор. Реранкер полезен как дополнительный инструмент, но его нельзя включать вслепую для всех вопросов: на части категорий он улучшает порядок выдачи, на стоимости может ухудшать результат.

Финальная техническая схема для запуска бота:

- чанкинг `fixed 700/100`;
- предобработка `heads`;
- retrieval `intfloat/multilingual-e5-small + BM25`;
- обогащение метаданных и поиск по `index_text`;
- reranker `mmarco` для части вопросов;
- генерация `Qwen2.5-7B-Instruct`;
- ответ только по контексту и с указанием источника.
